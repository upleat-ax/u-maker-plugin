# Deploy Target Matrix

> Capabilities and constraints per deploy target for `/u-deploy`. PBGD Deploy phase, v4.0.

## 1. Target catalog

| Target | Category | Typical artifact set | Notes |
|--------|----------|----------------------|-------|
| `vercel` | Edge / Serverless | `vercel.json`, CI pipeline, env-template, runbook | Best for SPA / SSR frontends |
| `netlify` | Edge / Serverless | `netlify.toml`, CI pipeline, env-template, runbook | Similar to Vercel; different config surface |
| `cloudflare-pages` | Edge | `wrangler.toml`, CI pipeline, env-template, runbook | Workers-compatible |
| `github-pages` | Static | `.github/workflows/pages.yml`, CI pipeline, runbook | Static output only; pairs well with `/u-output` |
| `docker` | Container | `Dockerfile`, `docker-compose.yml`, CI pipeline, env-template, runbook | Self-hosted or any container host |
| `cloud-run` | Container (managed) | `Dockerfile`, `service.yaml`, CI pipeline, env-template, runbook | GCP Cloud Run |
| `aws-amplify` | Managed frontend | `amplify.yml`, CI pipeline, env-template, runbook | AWS Amplify hosting |
| `aws-ecs` | Container | `Dockerfile`, `task-definition.json`, CI pipeline, env-template, runbook | Requires cluster/ALB context |
| `aws-lambda` | Serverless functions | `serverless.yml` or SAM template, CI pipeline, env-template, runbook | For BE-only deploys |
| `kubernetes` | Container (k8s) | `deployment.yaml`, `service.yaml`, `ingress.yaml`, Helm chart skeleton, CI pipeline, runbook | Any k8s cluster |
| `fly-io` | Container (managed) | `fly.toml`, CI pipeline, env-template, runbook | Fly.io |
| `railway` | Container (managed) | `railway.json`, CI pipeline, env-template, runbook | Railway |
| `render` | Container (managed) | `render.yaml`, CI pipeline, env-template, runbook | Render |
| `custom` | User-defined | `custom-deploy.sh`, runbook | Prompt user for a platform name; generate script skeleton only |

## 2. CI provider detection

When generating `ci-pipeline` artifacts, `/u-deploy` picks the provider:

| Detected repo file | CI provider used |
|--------------------|------------------|
| `.github/` | GitHub Actions → `.github/workflows/deploy-{target}.yml` |
| `.gitlab-ci.yml` (pre-existing) | GitLab CI → extends existing file |
| `bitbucket-pipelines.yml` (pre-existing) | Bitbucket Pipelines |
| (none) | Default: GitHub Actions (with a warning) |

## 3. Multi-target runs

Multiple targets can be selected in one invocation. The agent:

1. Generates a shared `runbook.md` referencing all targets.
2. Generates per-target CI jobs as separate workflow files.
3. Generates per-target platform configs independently.
4. Generates a single shared `env.example` with variables used by any of the targets, grouped by target.

## 4. Preview vs production

For platforms that support preview deployments (Vercel, Netlify, Cloudflare Pages, Amplify), the generated CI pipeline includes **two** jobs:

- `deploy-preview` — triggered on PRs
- `deploy-production` — triggered on main branch

For container/k8s targets, preview environments are not generated by default (requires user-level cluster/namespace setup). The runbook notes this as a TODO.

## 5. Secrets & env variables

The agent never writes secret values into artifacts. Instead, it:

- Lists required secret names in `env.example` and in the runbook.
- Adds a "Configure secrets in {CI}" step to the runbook.
- Marks the CI pipeline with `${{ secrets.* }}` or equivalent placeholders.

## 6. Adding a custom target

When the user selects `custom`, the agent prompts:

```
Custom target name (e.g., "on-prem-tomcat"):
Deploy method (ssh/scp/rsync/kubectl/other):
Target URL or host (optional):
```

Then generates:

- `deploy.sh` skeleton with the method selected.
- Runbook section template with blanks for the user to fill in.

No CI pipeline is auto-generated for `custom` unless the user also selects a CI provider explicitly.

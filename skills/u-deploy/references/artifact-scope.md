# Deploy Artifact Scope

> Detailed contents of each artifact type produced by `/u-deploy`. PBGD Deploy phase, v4.0.

## 1. `ci-pipeline`

CI workflow file(s) for the detected CI provider.

| Provider | File(s) | Template |
|----------|---------|----------|
| GitHub Actions | `.github/workflows/deploy-{target}.yml` (one per target) | `_meta/templates/ci-github-actions.template.yml` |
| GitLab CI | `.gitlab-ci.yml` (extended) | (inline rendering — no template) |

Each workflow includes: install, build, test, deploy steps. Secrets referenced as placeholders.

## 2. `platform-config`

Platform-specific config file. One per target.

| Target | Generated file(s) | Template |
|--------|-------------------|----------|
| vercel | `vercel.json` | `_meta/templates/ci-vercel.template.json` |
| netlify | `netlify.toml` | (inline) |
| cloudflare-pages | `wrangler.toml` | (inline) |
| docker | `Dockerfile`, `docker-compose.yml` | `_meta/templates/ci-docker.template.Dockerfile` |
| cloud-run | `Dockerfile`, `service.yaml` | composite (Docker + service YAML) |
| aws-amplify | `amplify.yml` | (inline) |
| aws-ecs | `Dockerfile`, `task-definition.json` | composite |
| aws-lambda | `serverless.yml` | (inline) |
| kubernetes | `deployment.yaml`, `service.yaml`, `ingress.yaml` | (inline) |
| fly-io | `fly.toml` | (inline) |
| railway | `railway.json` | (inline) |
| render | `render.yaml` | (inline) |
| github-pages | `.github/workflows/pages.yml` | (inline — covered by ci-pipeline) |

## 3. `deploy-script`

Shell script invokable locally to trigger a deploy. Example structure:

```
#!/usr/bin/env bash
# Generated by /u-deploy (v4.0) — target: {target}
set -euo pipefail
{target-specific deploy commands}
```

Placed at `.u-maker/deploy/{target}/deploy.sh` with `chmod +x`. The script never contains secrets.

## 4. `runbook`

Human-readable deployment runbook in Markdown. Template: `_meta/templates/deploy-runbook.template.md`.

Sections:

- Overview (what this runbook covers; targets; gate status)
- Pre-deploy checklist (gate passed, env vars set, preview verified)
- Deploy procedure (step-by-step for each target)
- Post-deploy verification (links to `smoke-test`)
- Rollback procedure (per target)
- Incident response contacts (placeholders for the team to fill)
- Change log reference (link to `release-notes`)

## 5. `env-template`

`.env.example` plus a secrets checklist in the runbook.

| File | Contents |
|------|----------|
| `.env.example` | All env var names grouped by concern (app, DB, 3rd-party APIs), with empty values and inline comments describing each |
| Runbook §"Configure secrets" | Table mapping env var → CI provider secret name → target(s) that need it |

Secrets are NEVER written as values — only names.

## 6. `release-notes`

Release-notes template. Generated at `docs/{app}/releases/{YYYY-MM-DD}-{version}.md` from `_meta/templates/release-notes.template.md`.

Sections:

- Summary (auto-populated from SRS delta)
- New features (from US items added since last release)
- Bug fixes (from test-results delta — failed→passed TCs)
- Breaking changes (from schema / API changes detected)
- Migration notes (if breaking changes exist)
- Known issues (from still-failing TCs)
- Contributors

The agent auto-detects "since last release" by reading `docs/{app}/releases/` for the most recent file.

## 7. `smoke-test`

Post-deploy smoke test checklist. Template: `_meta/templates/smoke-test.template.md`.

Generates a Markdown checklist (`- [ ]` items) derived from:

- High-priority TCs from `docs/{app}/gatekeeping/testcases.json` marked as `smokeRelevant: true`.
- One canonical path per IA top-level section (load the page, check the core CTA works).
- Health-check endpoint(s) from API spec.

The checklist is intentionally short — 10–20 items, runnable by a human in under 15 min.

## 8. Skipping artifacts

The user can always deselect any artifact. Recommended defaults (marked in the prompt as pre-selected): `ci-pipeline`, `platform-config`, `runbook`, `env-template`.
